The planned pipeline

For crates declared kernel, a gate would run five steps. None of them is built.

  1. 1 · extractExtract the kernel crate with Charon/Aeneas.
  2. 2 · driftCheck the extraction against the committed proofs/Extracted/.
  3. 3 · buildlake build the Lean proofs.
  4. 4 · auditAudit.lean: an axiom allowlist and the required claims.
  5. 5 · mutantsEach mutant must break exactly its named theorem.

Reproduced from docs/PLAN.md at 736c335.

Generalise writfold's gate: Charon/Aeneas extraction of the kernel crate → drift check against committed proofs/Extracted/ → lake build → Audit.lean (axiom allowlist + required claims) → mutants (each mutant must break exactly its named theorem). Three rungs: P0 property tests + cargo-mutants; P1 Kani from contracts ("bounded model-checked"); P2 Aeneas/Lean ("proved over the shipped Rust"). No Verus/Creusot.

Why the kernel tier exists

A kernel crate is no_std, has no floats, no HashMap, no shared mutability and no lint exceptions. That is the shape of code the proof tier is meant for:

The kernel's arithmetic and indexing rules duplicate what an Aeneas proof already establishes. The proof tier should subsume them; see the dry-run report. (docs/STATUS.md, Known gaps)

What it will claim

Only listed kernel theorems will be called proved, each named in a gate that runs on every commit. Nothing else on this site will be described that way.

Kill criterion

Proof tier can't be templated in 3 agent-days: ship without it. (docs/PLAN.md §9)
